- Tipo: feature.
- Estado: IMPLEMENTADO.
- Aprobación: Usuario indicó «aplicalo» en esta conversación el 2026-11-16.
- Objetivo: Integrar al dashboard actual del administrador un resumen de presencia y cortes diarios por empleado usando datos existentes de MotoZone.
- Alcance: Añadir al final del dashboard un panel responsive para el estado de sesión y actividad/corte por empleado del día, sin mover el contenido existente. Usar `PresenceService::onlineUsers()` desde el controlador y `DailyCutService::employeeBreakdown()` para hoy. Limitar las filas a personas con sesión activa o actividad/corte del día y enlazar cada fila a la consulta existente de corte por empleado y fecha; conservar también el composer de presencia del encabezado.
- Fuera de alcance: Sidebar, rutas y navegación; cambios o reordenamiento de módulos existentes; cambios a Caja, pantallas de corte, `PresenceService`, `DailyCutService` o `AppServiceProvider`; datos no existentes de turnos programados, asistencia, descansos, terminal, biometría o latencia; integración de pagos entrantes.
- Pasos: (1) Inyectar `DailyCutService` y `PresenceService` en `DashboardController`; preparar el desglose para `$generatedAt->toDateString()` y pasar la colección de sesiones al dashboard. El composer actual sigue alimentando el encabezado. (2) Añadir una sección al final de `dashboard.blade.php` con resumen de sesiones activas, personas con actividad hoy y cortes generados; mostrar filas con nombre, estado de sesión, tickets/ventas y estado del corte. Incluir empleados con sesión activa o actividad/corte (tickets, ventas, efectivo entrante/saliente, devolución o snapshot), evitando etiquetas que impliquen asistencia/turno. (3) Enlazar el detalle a `pos.cuts.index` con `date` y `employee`, conservando la autorización existente. (4) Ampliar `AdminTest.php` para cubrir actividad/corte, sesiones recientes frente a expiradas, enlace, estado vacío, acceso admin y ausencia de cambios a los módulos existentes; validar la vista en viewport móvil.
- Archivos afectados: `app/Http/Controllers/Admin/DashboardController.php` (preparar datos diarios); `resources/views/admin/dashboard.blade.php` (panel nuevo al final, accesible y responsive); `tests/Feature/AdminTest.php` (pruebas del contrato visible y los datos). No modificar `routes/web.php`, `resources/views/layouts/admin.blade.php`, `AppServiceProvider.php`, los servicios de presencia/corte ni vistas de Caja/corte.
- Criterios de aceptación: (1) Solo datos de sesiones, ventas y cortes reales. (2) “En línea” significa sesión activa en ventana de 5 minutos, no presencia física. (3) Se muestran personas con sesión activa o actividad/corte hoy, no empleados inactivos sin datos como si tuvieran un turno pendiente. (4) Los importes/tickets coinciden con el desglose del corte diario. (5) Cada enlace consulta el empleado y fecha correctos en el destino existente. (6) Con cero actividad, se muestra un estado vacío claro. (7) Sidebar, navegación y posición/orden relativo de módulos actuales no cambian. (8) Diseño legible y operable en móvil.
- Plan de rollback: Retirar la sección añadida al final de `dashboard.blade.php`, revertir únicamente la preparación de datos en `DashboardController.php` y las aserciones nuevas en `AdminTest.php`; no hay migraciones, cambios de rutas ni datos persistidos que revertir.
- Riesgos: `employeeBreakdown()` construye el desglose por usuario y puede generar varias consultas; el costo crece con el número de empleados. El controlador hará una lectura adicional de presencia en `/admin` mientras el composer existente mantiene la suya para el encabezado. `PresenceService` devuelve lista vacía si `session.driver` no es `database`. La ventana de cinco minutos mide sesión reciente, no asistencia. Excluir los datos sin fuente evita inventar métricas. El bug histórico de reapertura de corte figura resuelto por `fix-corte-reabrir-dia-01`; esta feature no modifica ese flujo.
- Alternativas consideradas: Reutilizar sin cambios el partial extenso de Caja; descartado porque su presentación es específica de esa pantalla y usa etiquetas de turno/asistencia que no son fuente fiable para este dashboard. Crear una pantalla o endpoint separado; descartado para no duplicar módulos, navegación ni infraestructura. La opción de usar el composer del layout para la sección del dashboard se descartó: Laravel renderiza el contenido hijo antes del composer del layout. El usuario autorizó la consulta directa del controlador, aceptando una lectura de presencia adicional en `/admin` y dejando `AppServiceProvider` intacto.
- Dependencias: datos y permisos ya existentes; el rol admin tiene `pos.cut.manage` para consultar `pos.cuts.index`.
- Verificación: pruebas de feature enfocadas en `tests/Feature/AdminTest.php`; revisar que los links respeten el filtro `date`/`employee` y que la vista compartida `layouts.admin` continúe entregando `onlineUsers`.
- Skills: `ponytail`, `laravel-best-practices`, `tailwindcss-development` y `testing-best-practices` aplican; no hay skills disponibles de `code-search`, `memory-sync`, PostgreSQL o E2E. MCP de memoria y `codesearch_*` no están disponibles; memoria respaldada en `.memory/` y exploración local realizada. `.ai/rules` no existe.
- Desviación autorizada: 2026-11-16, `PresenceService::onlineUsers()` se invoca también desde el controlador porque la variable del composer padre no está disponible al evaluar el contenido hijo; se conserva el composer del encabezado y no se modifica `AppServiceProvider`.
- Cambios aplicados: Inyección de `DailyCutService` y `PresenceService` en `DashboardController`; panel responsive al final del dashboard con resumen y filas filtradas por sesión/actividad/corte del día; enlaces a `pos.cuts.index`; pruebas de datos, sesiones recientes/expiradas, enlaces y estado vacío añadidas a `AdminTest.php`.
- Verificación: Pint, `php -l` de los dos archivos PHP modificados, compilación Blade (`view:cache` seguida de `view:clear`) y `git diff --check` correctos. No se ejecutaron pruebas; Testing requiere solicitud explícita.
- Riesgo observado: `employeeBreakdown()` itera los usuarios con roles admin/empleado y ejecuta el cálculo por usuario antes de filtrar filas para el panel; el costo puede crecer con el equipo.
- Última actualización: 2026-11-16.
